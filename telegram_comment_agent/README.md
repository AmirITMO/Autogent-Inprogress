# telegram_comment_agent

Отдельный сервис — источник трафика «Автокомментинг в Telegram». Юзербот
слушает посты в целевых чужих каналах, предлагает черновик комментария под
каждый подходящий пост; публикует ТОЛЬКО то, что сотрудник одобрил в CRM
(раздел «Каналы трафика» → «Автокомментинг в Telegram»). Никакого полного
автопостинга без одобрения нет.

## Почему одобрение обязательно (риски)

Массовые автоматические комментарии от одного аккаунта под разные посты в
короткий срок — классический паттерн, который Telegram детектит агрессивнее,
чем простое чтение (парсинг скаута): аккаунт активно пишет, а не только
читает. Смягчение уже встроено в код:

- **Ручное одобрение перед публикацией** (`sender.py` публикует только
  `APPROVED`-черновики) — при этом и человек видит текст до того, как он
  уйдёт в чужой канал, и сам факт "решение принимает человек" сбивает темп
  публикаций естественным образом.
- **Дневной лимит** (`MAX_COMMENTS_PER_DAY`, по умолчанию 15) и **минимальная
  пауза между публикациями** (`MIN_DELAY_BETWEEN_COMMENTS_SECONDS`, по
  умолчанию 180с) — `throttle.py`, действуют даже если сотрудник одобрил
  сразу пачку черновиков.
- Комментарий пишется как «живая реплика» без рекламных штампов и ссылок
  (см. `comment_writer.SYSTEM_PROMPT`) — палевный шаблонный текст быстрее
  ловит жалобы читателей канала.

Чего код не решает: ротацию нескольких аккаунтов (снижает риск для каждого
отдельного акка, но кратно увеличивает совокупный риск — сознательно не
делаем по умолчанию), "прогрев" аккаунта и постепенное добавление целевых
каналов — это ручные операционные практики, не автоматизируются намеренно
(см. тот же принцип в `telegram_sales_agent/README.md`, раздел «Скаут-only
аккаунты»).

## Как работает

1. При старте читает базу знаний канала (`GET .../knowledge-base`) —
   продукт, тон, список целевых каналов, критерии "что комментировать/что
   пропускать", заполняется через чат «Управление» в CRM.
2. `comment_writer.extract_target_channels` одним вызовом OpenAI достаёт из
   текста базы знаний список @юзернеймов целевых каналов.
3. `monitor.py` подписывается на новые посты в этих каналах через Telethon
   (`events.NewMessage`). Для каждого поста — `should_comment` решает,
   стоит ли он комментария, `draft_comment` пишет текст.
4. Черновик пушится в CRM (`POST .../drafts`, статус `PENDING`) —
   сотрудник видит его во вкладке «Подробности», может отредактировать
   текст, одобрить или отклонить.
5. `sender.py` раз в `POLL_INTERVAL_SECONDS` спрашивает CRM про одобренные
   черновики (`GET .../drafts?status=approved`, claim-on-read → `IN_PROGRESS`)
   и публикует их как комментарий под исходным постом (Telethon
   `send_message(..., comment_to=post_id)` — сам резолвит привязанную
   группу обсуждений канала), с учётом дневного лимита и паузы.
6. Результат — `POST .../drafts/:id/complete` (`SENT` или `FAILED`).

Список целевых каналов читается один раз при старте процесса — изменение
темы «В каких каналах комментировать» в CRM требует перезапуска сервиса,
чтобы подхватиться (осознанное упрощение MVP).

## Переменные окружения (`.env`, рядом с этим файлом, не коммитить)

| Переменная | Назначение |
|---|---|
| `CRM_API_URL` | базовый адрес CRM, например `https://crm.autogentgroup.ru` |
| `TG_AUTOCOMMENT_AGENT_API_KEY` | тот же секрет, что в `.env.production` CRM |
| `CRM_CHANNEL_ID` | id канала «Автокомментинг в Telegram» в CRM (найти в URL страницы канала) |
| `OPENAI_API_KEY` | свой ключ, для отбора постов и написания комментариев |
| `TG_API_ID` / `TG_API_HASH` | Telegram API credentials юзербот-аккаунта (my.telegram.org) |
| `TG_SESSION_PATH` | куда сохранять сессию Telethon, по умолчанию `sessions/comment_agent` |
| `TG_PROXY_HOST`/`_PORT`/`_USERNAME`/`_PASSWORD` | SOCKS5-прокси, если сервер не может напрямую достучаться до Telegram |
| `POLL_INTERVAL_SECONDS` | интервал опроса CRM за одобренными черновиками, по умолчанию 30 |
| `MAX_COMMENTS_PER_DAY` | дневной лимит публикаций, по умолчанию 15 |
| `MIN_DELAY_BETWEEN_COMMENTS_SECONDS` | минимальная пауза между публикациями, по умолчанию 180 |

## Локальный запуск

```bash
pip install -r requirements.txt
# создать .env с переменными из таблицы выше
python main.py
```

Первый запуск запросит вход в Telegram (номер телефона/код) и сохранит
сессию в `TG_SESSION_PATH` — дальше использует её.

## Docker

```bash
docker compose up -d --build
```

## Тесты

```bash
pip install -r requirements.txt
pytest
```

`comment_writer.py`, `crm_client.py`, `throttle.py` покрыты тестами
(OpenAI/HTTP замоканы, sqlite — во временном файле, без сети). `monitor.py`
и `sender.py` НЕ покрыты — требуют реального Telethon-клиента, тот же
принцип, что у `offer_writer.py` в `instagram_scout_service`.
