## 2026-08-15 — Instagram-скрейпинг через aiograpi, один реальный аккаунт
Спайк (`spikes/FINDINGS.md`): официальный Graph API не даёт поиска по
чужим аккаунтам в принципе. aiograpi — единственный реалистичный путь.
Без прокси-ферм, с паузой между запросами — та же граница, что уже была
согласована раньше в проекте (парсинг можно, автоматизацию рассылки
и обход детекции — нет).

## 2026-08-15 — Аудит нашёл критичный дефект: criteria.keywords не был гарантирован контрактом
`scraper.py` читал `criteria["keywords"]`, а tool-схема `save_search_profile`
в `instagramSearch.ts` принимала `criteria` как свободный `object` без
описанных полей — LLM могла сохранить любые ключи, и парсинг молча находил
0 аккаунтов без единой ошибки. **Исправлено**: схема тула сужена до explicit
`{ keywords: string[], niche?, city?, excludeIf? }`. Урок: там, где два
процесса (TS и Python, LLM tool-call и потребитель JSON) обмениваются
свободной JSON-структурой без общей схемы — она обязана быть описана явно
в обеих точках, а не только в одной.

## 2026-08-15 — Аудит нашёл: джоб привязывался к «последнему профилю канала» вместо профиля текущего диалога
Реальный баг, не крайний случай — по системному промпту количество
аккаунтов спрашивается СЛЕДУЮЩИМ сообщением после сохранения профиля,
то есть `savedProfileId` внутри одного вызова `sendSearchSetupMessage`
всегда был `null` на шаге `create_scrape_job` в штатном сценарии.
**Исправлено**: `profileId`, возвращённый после `save_search_profile`,
явно возвращается клиенту и передаётся обратно на следующий вызов —
сервер больше не угадывает. Добавлен регрессионный тест с «ловушкой»
(в канале намеренно создан другой недавний профиль).

## 2026-08-15 — Аудит нашёл: IN_PROGRESS был мёртвым статусом
Упавший сервис оставлял джоб в PENDING навсегда «в работе»; при перезапуске —
полный повторный прогон (повторные платные вызовы OpenAI). **Исправлено**:
`GET jobs?status=PENDING` теперь атомарно переводит выданные джобы в
IN_PROGRESS («claim on read»). Это защита для единственного экземпляра
сервиса — если когда-нибудь понадобится несколько параллельных
экземпляров, потребуется настоящая блокировка (SELECT FOR UPDATE SKIP LOCKED
или аналог), это НЕ сделано сейчас, т.к. вне текущего скоупа (один сервис,
один Instagram-аккаунт).

## 2026-08-15 — Принятые ограничения, не исправленные в этой сессии
- `instagram_scout_service/scraper.py` и `offer_writer.py` не тестировались
  против реального Instagram-аккаунта/реального OpenAI — нет учётных
  данных в этой сессии. `main.py`/`scraper.py`/`offer_writer.py` не
  покрыты автотестами (только `crm_client.py`, 6/6).
- `instagram_scout_service/.env.example` не создан — permission-система
  песочницы блокирует запись любого файла `.env*` независимо от
  содержимого. Переменные задокументированы в README.md сервиса.
- `.env.production.example` (корень CRM) не обновлён новыми именами
  переменных (`OPENAI_API_KEY`, `SCOUT_AGENT_API_KEY`,
  `INSTAGRAM_AGENT_API_KEY`, `B2B_EMAIL_AGENT_API_KEY`) — задача T-11 в backlog.
- UI Instagram-канала не показывает статус/ошибку джобов — задача T-12.
- `sendManagementMessage` (общий чат-редактор базы знаний, используется
  и скаутом, и email-каналом) не покрыт тестами — задача T-13.
- brief.md обещал «три вкладки» для обоих новых каналов; у Instagram по
  дизайну их нет (это таблица/очередь заданий, не диалоговые карточки) —
  расхождение brief↔plan, не баг, план был точнее исходного брифа.
- Весь результат сессии (два коммита стадии 7 + фиксы аудита) не
  закоммичен — коммитим только по явной просьбе пользователя (правило
  скилла `/pipeline`, не изменено).
