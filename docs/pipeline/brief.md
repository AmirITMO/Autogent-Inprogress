# Brief

## Что система делает сейчас (факт, brownfield)

Autogent Platform — внутренняя CRM (Next.js 16 + Prisma + Postgres, деплой
Docker Compose на `crm.autogentgroup.ru`). Раздел «Каналы трафика» — общий
список источников лидов с финансовыми метриками (выручка/затраты/ROI/CAC),
плюс у каналов с типом ≠ MANUAL есть детальная страница `/channels/[id]`.

Для канала «ИИ-скаут» (`SCOUT_TELEGRAM`) эта страница уже построена по
образцу, который теперь надо повторить для пунктов 2 и 3:

- Три вкладки: **Управление** / **Аналитика** / **Подробности**.
- **Управление** — чат с LLM (OpenAI, tool-calling), читает/переписывает
  `AgentKnowledgeBase.content` (текст, `.md`-подобный) через tool
  `update_knowledge_base`. История диалога — `AgentKbMessage`. Кнопка
  «Пройти опрос по продукту» — тот же чат в режиме структурированного
  интервью.
- **Аналитика** — 7 метрик (лидов принесено, выручка, затраты, ROI, CAC,
  отказов, конверсия текст→созвон), расчёт в `lib/channelFinancials.ts`.
- **Подробности** — контакты (диалоги) + сводка + тренды + health
  аккаунтов, из `ScoutAgentContact`/`ScoutAgentMetricSnapshot`.
- Обе таблицы (`AgentKnowledgeBase`, `AgentKbMessage`) уже **не** привязаны
  к скауту в названии — ключ `channelId`, схема общая на все типы каналов.
- Внешний Python-агент (`telegram_sales_agent/`, отдельный git-subtree в
  этом же репозитории) не имеет публичного адреса — весь обмен только
  **pull**: агент сам ходит в CRM за данными (`GET .../knowledge-base`) и
  сам шлёт результаты (`POST .../contacts`, `/leads`, `/metrics`). CRM
  никогда не инициирует запрос к агенту напрямую.
- Авторизация интеграций — заголовок `X-Api-Key`, свой секрет на каждого
  агента (`SCOUT_AGENT_API_KEY`, аналогично для будущих).
- Модель данных `Instagram*`/`B2bEmail*` (Contact + MetricSnapshot) уже
  заведена в схеме заранее (миграция от 2026-08-14), но UI под них сейчас
  — старые пассивные дашборды без вкладок Управление/Аналитика и без
  триггера парсинга из CRM.

## Что хотим построить (эта сессия)

### Пункт 2 — Instagram-канал
CRM-инициированный сбор базы: кнопка «Спарсить N аккаунтов» (N < 50) →
диалог с LLM, который задаёт ~5 вопросов, чтобы понять критерии целевого
лида → сохранённый «профиль поиска» (для повторного запуска) → запрос
уходит в очередь заданий на стороне CRM → **новый, отдельный сервис**
опрашивает CRM раз в ~30 секунд, видит задание, парсит N Instagram-
аккаунтов по критериям, сам генерирует черновик сообщения на каждый
аккаунт (свой вызов LLM) и пушит результат в CRM тем же паттерном
push-контактов, что уже есть (`InstagramContact`).

Скрейпинг — только чтение публичных данных аккаунта, без автоматической
отправки сообщений и без инженерии обхода анти-спам/анти-бот защиты
площадки (граница, зафиксированная раньше в этом же проекте — не
пересматривается).

### Пункт 3 — Email-канал
Точное повторение архитектуры скаута для канала `B2B_EMAIL`: те же три
вкладки, тот же чат-редактор (переиспользуем `AgentKnowledgeBase`/
`AgentKbMessage`/`sendManagementMessage` — они уже общие по `channelId`,
не специфичны для скаута), та же «Аналитика» через существующий
`computeChannelFinancials`. Новое — только pull-эндпоинт базы знаний под
`b2b-email-agent` (по образцу scout-agent) и подключение к существующему
`B2bEmailDashboard`.

## Ограничения
- Не пересматриваем этическую границу по обходу анти-спам защит площадок
  (решено раньше в этом проекте).
- Секреты — только именами переменных, значения не вписываются в артефакты.
- Новый Instagram-сервис — вне текущего Next.js/Prisma репозитория по
  функциональности, но код (если делаем сейчас) физически может лежать
  рядом, аналогично `telegram_sales_agent/`.

## Решения этой сессии (голосом пользователя)
- Instagram-парсинг — отдельный новый сервис, не расширение `telegram_sales_agent`.
- Черновик сообщения на аккаунт генерирует сам агент (не CRM).
- Интервал polling — ~30 секунд.
- Email-канал — точное повторение паттерна скаута, без отличий.
